# WinWin v2 Professional Care Record UX & Visual Design Review Draft

> 文件狀態：Design Review Draft
>
> 本輪 Gate：規格審查，不含實作
>
> 適用階段：未來專業紀錄 Prototype 與正式版設計輸入
>
> 最後更新：2026-08-25

## 0. 決策摘要

- 專業紀錄區延續 WinWin 的霧藍、暖奶白、圓潤與可信任感，以 `#3B6978` 作為唯一主要互動色；森林綠只作成功或穩定狀態的輔助色。
- 第一條 Prototype flow 建議採「手機分段步驟／桌面左側段落導覽」的同一份六區段表單模型，不以裝置切換不同資料結構。
- Prototype 僅為 in-memory 流程展示，不得宣稱自動儲存、雲端保存或可安全離開；離頁前必須清楚說明可能遺失。
- Sticky Action Bar 可進入 Prototype 驗證，但須先滿足內容避讓、safe area、鍵盤、200% zoom 與無 blur 退化條件。
- Dark Mode 延後；沒有正式淺色 Logo 與完整暗色狀態驗證前，不進入實作。
- 本文件中的「低干擾、閱讀舒適、降低資料遺失焦慮」均為設計目標或待驗證假設，不是已證實成效。

## 1. 適用與排除範圍

### 1.1 適用範圍

本規格只適用於未來專業人員進行下列工作時的介面：

- 新增照顧紀錄。
- 建立專業評估紀錄。
- 閱讀與輸入長篇 Observation（觀察與主述）。
- 記錄處置或服務內容。
- 建立後續追蹤事項。
- 暫存草稿、確認與送出紀錄。
- 依時間檢視單一個案的專業紀錄歷程。

這些畫面屬於高密度、長時間、以閱讀與輸入為主的工作介面，可比一般品牌頁面更沉靜，但仍須明確屬於 WinWin。

### 1.2 排除範圍

本規格不直接套用於：

- 身分註冊與登入。
- 邀請建立、驗證與接受。
- 家屬簡易提問。
- 多個案首頁或工作空間總覽。
- 一般導覽。
- WinWin 品牌首頁。

本文件也不定義專業權限、資料保留政策、臨床術語、評估量表、後端資料模型或法規遵循結論；這些須由對應產品、專業、法務與工程文件另行決定。

## 2. 設計目標與證據限制

### 2.1 設計目標

專業紀錄介面以以下品質為目標：

- 低視覺干擾：減少不必要裝飾、強烈陰影與競爭性強調。
- 清楚資訊層級：讓個案、紀錄狀態、區段標題、欄位與操作層級可快速辨識。
- 長篇閱讀舒適：控制行長、字級、行高與段落節奏。
- 長表單分段：讓使用者理解目前位置、完成度及剩餘工作。
- 降低資料遺失疑慮：如實呈現資料是否已持久化及離頁風險。
- 防止誤觸：區分暫存、取消、下一步與送出，危險或不可逆操作要求確認。
- 效率與可及性並重：支援鍵盤、螢幕閱讀器、放大、觸控與不同視窗寬度。

期望語氣為冷靜、秩序、包容、專業，但不冰冷，也不仿造傳統醫療表格的高密度格線。

### 2.2 證據限制

上述項目目前是設計目標與待驗證假設。未完成專業人員可用性測試或取得可靠研究來源前，不得對內或對外宣稱本設計已科學證明能：

- 降低認知負荷。
- 減少眼睛疲勞。
- 降低焦慮。
- 提升紀錄正確率或完成速度。

專題報告若描述成效，須清楚區分「設計意圖」「測試觀察」與「可推論結論」，並附使用者測試方法、樣本限制或可靠來源。沒有證據時，應使用「旨在」「預期」「待驗證」，不得使用「能夠降低」「已改善」等確定語氣。

## 3. 與 WinWin 品牌的整合原則

### 3.1 必須保留

- WinWin Logo 與既有名稱。
- 霧藍、暖奶白的品牌感。
- 圓潤、溫和、可信任的視覺語言。
- 黃色向日葵作為品牌識別；在工作區中宜低頻出現，不作為每個狀態或 CTA 的裝飾。

### 3.2 專業工作區調整

- 工作畫布可採較中性的冷灰，內容 Surface 保持白色，讓長篇資訊比品牌首頁更安靜。
- `#3B6978` 是主要互動色，用於主要 CTA、目前導覽位置、focus 邊界與必要連結。
- 不新增森林綠作第二套主色。森林綠只用於「已完成／穩定」等正向狀態，且必須搭配文字或圖示。
- 圓角與柔和陰影延續品牌性格，但不能使專業紀錄看起來像行銷卡片集合。
- Logo 周圍保留足夠淨空；不得拉伸、裁切、改色或以 CSS filter 製造正式反白版本。

### 3.3 品牌一致性檢核

每次視覺審查至少回答：Logo、主要互動色、Surface、圓角語言與文字語氣是否仍可辨識為 WinWin；若移除 Logo 後完全像另一套後台產品，應重新調整共用 Shell 與品牌節點，而不是增加更多裝飾色。

## 4. Color／Typography／Spacing Tokens

### 4.1 Color tokens

| Token | 值 | 用途 |
| --- | --- | --- |
| `color.canvas` | `#F4F6F8` | 專業工作區畫布 |
| `color.surface` | `#FFFFFF` | Card、Action Bar、主要內容面 |
| `color.text.primary` | `#1E293B` | 標題、正文、輸入文字 |
| `color.text.secondary` | `#64748B` | 輔助說明、時間、次要 metadata |
| `color.accent.primary` | `#3B6978` | 主要 CTA、focus、目前位置 |
| `color.field.subtle` | `#F8FAFC` | 未聚焦輸入區背景 |
| `color.divider` | `#E2E8F0` | 分隔線與極淡邊界 |

狀態色：

| 狀態 | 背景 | 文字 | 必要非色彩提示 |
| --- | --- | --- | --- |
| 追蹤中 | `#E0F2FE` | `#0369A1` | 「追蹤中」文字；必要時加進行中圖示 |
| 已完成／穩定 | `#DCFCE7` | `#15803D` | 「已完成」或「穩定」文字與完成圖示 |
| 待處理／注意 | `#FEF3C7` | `#B45309` | 「待處理」或「注意」文字與提示圖示 |

這組值是候選 tokens，不代表所有前景／背景、hover、disabled、focus 與圖示組合已驗證。實作前須以實際字級、字重與元件狀態逐一檢查 WCAG 對比；狀態永遠不得只靠顏色表達。

候選色的初步 sRGB 相對亮度計算如下；這只驗證指定純色配對，不代表整個元件、透明度、實際字重或互動狀態已通過：

| 前景／背景 | 計算對比 |
| --- | ---: |
| Primary Text `#1E293B`／Surface `#FFFFFF` | `14.63:1` |
| Secondary Text `#64748B`／Surface `#FFFFFF` | `4.76:1` |
| Primary Accent `#3B6978`／Surface `#FFFFFF` | `6.04:1` |
| 追蹤中文字 `#0369A1`／背景 `#E0F2FE` | `5.17:1` |
| 已完成文字 `#15803D`／背景 `#DCFCE7` | `4.57:1` |
| 待處理文字 `#B45309`／背景 `#FEF3C7` | `4.51:1` |

上述配對在數值上達到一般文字 `4.5:1` 的候選門檻，但後兩組接近邊界；實作時不得加入降低對比的 opacity，並須在目標螢幕、字級、字重、瀏覽器縮放及高對比模式重測。非文字控制項與 focus indicator 另依其相鄰色及實際幾何驗證。

### 4.2 Typography tokens

字型 fallback：

```css
--font-zh: "PingFang TC", "Noto Sans TC", system-ui, sans-serif;
--font-latin: "Inter", system-ui, sans-serif;
```

第一版應優先使用系統已有字型。若要載入 Noto Sans TC 或 Inter，須先審查字型檔大小、使用字重、subset、載入策略與失敗退化，不得只為單一頁面加入過大的字型依賴。

| 角色 | 字級 | 字重 | Line height | 備註 |
| --- | ---: | --- | ---: | --- |
| 個案姓名／頁面主標題 | `20px` | Semi-Bold（600） | `1.3` | 不依賴超大字形成層級 |
| 區塊標題 | `16px` | Medium（500） | `1.4` | 六個主要區段一致 |
| 長篇紀錄 | `15–16px` | Regular（400） | `1.7` | 建議閱讀行長約 60–75 個拉丁字元；中文須實機驗證 |
| Label（手機） | 至少 `14px` | Medium 或 600 | `1.4–1.5` | 永久可見 |
| Label（桌面） | `13–14px` | Medium 或 600 | `1.4–1.5` | 不以 placeholder 取代 |
| Input 文字（手機） | 至少 `16px` | Regular | `1.5` | 避免 iOS 聚焦自動放大並維持可讀性 |

專業紀錄正文不建議使用裝飾性襯線標題字；若共用 Shell 保留品牌標題字，應限於品牌節點，不進入密集表單與長篇紀錄內容。

### 4.3 Spacing tokens

以 4px 基準建立一致間距：

| Token | 值 | 主要用途 |
| --- | ---: | --- |
| `space.1` | `4px` | 圖示與緊密文字微調 |
| `space.2` | `8px` | Label 與輸入區、相關 metadata |
| `space.3` | `12px` | 小型元件內距 |
| `space.4` | `16px` | 一般內距、行動版水平 gutter 下限 |
| `space.5` | `20px` | Card padding、欄位間距下限 |
| `space.6` | `24px` | 欄位間距上限、區段內群組 |
| `space.8` | `32px` | 區段之間 |
| `space.10` | `40px` | 大區段分隔（視 viewport 調整） |

欄位間垂直距離使用 `20–24px`；錯誤文字屬於欄位本身，放在控制項下方 `8px`，不能因出現錯誤而讓關聯變得不清楚。

## 5. Card、Input、Textarea、Pill、CTA 規格

### 5.1 Card

- Padding：`20px`。
- Background：`#FFFFFF`。
- Border radius：`16px`。
- Shadow：`0 2px 12px rgba(15, 23, 42, 0.04)`。
- 預設不使用深色框線；若 Surface 與 Canvas 在實機或高亮環境下分界不足，可加 `1px solid #E2E8F0`。
- Card 不應層層巢狀。優先用標題、留白與 divider 表達區段；一個視覺層級通常只需一層 Card。

### 5.2 Input／Select

- Minimum height：`48px`。
- Padding：`12px 16px`。
- Background：`#F8FAFC`。
- Border radius：`10px`。
- 預設仍須保有可辨識邊界；可用 `1px solid #E2E8F0`，不可只靠背景差。
- Focus：背景轉為 `#FFFFFF`，邊界 `1.5px solid #3B6978`，並有不被裁切的柔和外圈。
- Focus 不得只靠背景變化；forced-colors 下須保留系統可見 outline。
- Disabled、read-only 與 unavailable 必須視覺及語意不同；disabled 不可單靠降低 opacity 到難以閱讀。
- 必填狀態應以文字或符號搭配說明，不能只以紅色星號傳達。

### 5.3 Textarea

- 套用 Input 的背景、邊界、圓角、padding 與 focus 規則。
- 依內容自動增高，但設定合理最小與最大高度。第一版候選：短欄位最小 `120px`、長篇 Observation 最小 `192px`；最大高度以 viewport 與裝置測試決定。
- 超過安全高度後才使用內部捲動，且內部捲動區必須可鍵盤到達、具可見 focus，並避免形成難以察覺的巢狀捲動。
- 若允許手動 resize，預設只允許垂直方向，設定最大寬度與高度，不能破壞父容器或遮住 Action Bar。
- 自動增高不能無限制延伸頁面；使用者仍須能找到欄位標題、錯誤與操作列。
- 顯示字數或長度限制時，須說明限制與剩餘量；不能只在超限後顯示錯誤。

### 5.4 Status Pill

- Minimum height：`28px`。
- Padding：`6px 12px`。
- Border radius：`999px`。
- 內容必須有明確狀態文字；如使用圖示，圖示是補充而非唯一訊息。
- Pill 若不可操作，不應使用按鈕 hover 或 pointer cursor。
- 多個狀態並存時，先定義優先層級，避免一列充滿不同顏色標籤。

### 5.5 CTA 與其他可點擊元件

- CTA minimum height：`48px`。
- CTA minimum width：`120px`；窄螢幕可改為滿寬或換行，不能造成水平捲動。
- Border radius：`12px`。
- 所有觸控目標至少 `44 × 44px`，圖示按鈕也包含在內。
- 同一畫面只保留一個最主要動作。暫存草稿、下一步與送出不可同時都用最高強調。
- 「送出紀錄」與「暫存草稿」使用不同名稱、位置與視覺層級；送出前提供確認摘要。
- 「取消」不應緊鄰主要 CTA 到容易誤觸；若會捨棄未保存內容，須二次確認。
- Loading、disabled、success 與 error 皆須有文字或語意狀態，且避免重複送出。

## 6. 長表單分段方案比較

所有候選方案共用六個語意區段：

1. 本次服務基本資訊。
2. 觀察與主述。
3. 評估內容。
4. 處置或服務紀錄。
5. 後續追蹤。
6. 確認與送出。

### 6.1 方案比較

| 裝置／方案 | 優點 | 風險 | 鍵盤與螢幕閱讀器要求 | 第一版判定 |
| --- | --- | --- | --- | --- |
| 手機：步驟式流程 | 一次聚焦少量內容；進度與下一步清楚 | 跨區錯誤可能被隱藏；來回成本較高 | 步驟名稱與目前位置需可讀；切換後管理標題 focus；返回不得清空 | **建議驗證**，適合線性初次輸入 |
| 手機：Accordion | 可在同頁快速展開；保留上下文 | 長內容仍可能失控；多層展開使位置難追蹤 | Button 語意、`aria-expanded`、`aria-controls`；不得自動關閉含錯誤區段 | 次選，適合熟練者快速跳段 |
| 手機：分段頁面 | URL／狀態邊界清楚；每頁負擔較小 | Prototype 無持久化時跨頁狀態與離頁風險更高 | 頁面標題、返回策略、錯誤摘要與狀態保存都要定義 | 暫不優先，除非路由與草稿模型已明確 |
| 平板：分段頁面 | 可維持大觸控目標與適中行長 | 頻繁換頁；橫直向差異大 | 同手機分段頁面，並測外接鍵盤 | 可作退化方案 |
| 平板：Tabs | 快速切區且可保留同頁狀態 | Tabs 擁擠或換行；未讀錯誤易藏在其他 tab | 標準 tablist／tab／tabpanel 操作與方向鍵；tab 名稱顯示錯誤數 | **建議驗證**，僅在六個標籤可容納時 |
| Desktop：Tabs | 熟悉、快速、節省垂直空間 | 六區段標籤較長；跨 tab 驗證可見性差 | 完整 ARIA tabs pattern；不可只靠色彩顯示 active／error | 次選，適合內容量較均衡的版本 |
| Desktop：左側段落導覽 | 一眼看見整體結構、完成與錯誤位置；適合長頁閱讀 | 需要同步捲動與 sticky 邏輯；窄視窗需退化 | 導覽用連結或按鈕；目前位置不強制搶 focus；skip link 與 landmark 清楚 | **第一版優先** |

### 6.2 建議架構

第一版使用同一份六區段表單狀態：

- 320px／375px：一次呈現一個步驟；頂部顯示「步驟 2／6」及區段名稱，可返回且內容保留。
- 768px：優先測試可水平容納的 Tabs；若 200% zoom 或標籤換行後不可用，退化為步驟選單或單欄段落導覽。
- 1440px：左側段落導覽加右側單欄內容；閱讀欄避免過寬。

這是呈現方式的響應式調整，不是三套不同 flow。欄位、驗證規則、區段 ID 與資料狀態必須一致。

### 6.3 進度、返回與跨區錯誤

- 進度至少呈現目前區段與總區段數；「完成」只在該區必填驗證通過後顯示。
- 不以進度百分比暗示剩餘時間，除非已驗證各區工作量相近。
- 返回前一區段或在導覽間切換，必須保留目前 session 內內容、游標可預期位置與錯誤狀態。
- 即時驗證以不打斷輸入為原則；一般格式錯誤可在 blur 後顯示，送出時完整驗證。
- 送出失敗時，頁面頂端顯示可聚焦的錯誤摘要，列出每個錯誤並連回欄位；對應區段導覽同時顯示文字／圖示／錯誤數。
- 不得因區段未開啟而隱藏重要錯誤。導向錯誤時先開啟區段，再將 focus 移至欄位或其錯誤摘要連結的合理目標。

## 7. 草稿與未儲存內容狀態

### 7.1 In-memory Prototype

Prototype 沒有可靠持久化時，固定顯示：

> 此為流程展示，內容只保留在目前頁面；重新整理後會重置。

此提示應在開始輸入前可見，並在 Action Bar 或頁面狀態區持續容易找到。不得顯示或暗示：

- 已自動儲存。
- 已保存至雲端。
- 可以安全離開。
- 任何看似真實的最後儲存時間。

使用者已有未送出內容並嘗試離開此 flow 時，顯示：

> 這份紀錄尚未保存，離開後可能遺失。

對站內可攔截導覽，對話框提供「繼續編輯」與「離開並捨棄」；安全選項取得初始 focus。瀏覽器重新整理、關閉分頁或返回的原生警告能力有限，Prototype 不得承諾所有離頁情境都能顯示自訂文字。

### 7.2 未來正式持久化狀態

只有後端確認寫入成功，且回傳可對應目前草稿版本的結果後，才能顯示：

> 已於 10:42 儲存草稿

正式版須定義完整狀態機：

| 狀態 | 顯示原則 | 可用動作 |
| --- | --- | --- |
| 儲存中 | 顯示正在處理，不宣稱完成 | 避免重複儲存；使用者可繼續輸入與否須由版本策略決定 |
| 已儲存 | 顯示後端確認時間與草稿語意 | 繼續編輯、送出 |
| 儲存失敗 | 清楚說明尚未保存，不清空本地內容 | 再次嘗試、複製內容或其他復原途徑 |
| 離線 | 說明目前無法確認遠端保存 | 重新連線、再次嘗試；若有離線佇列須明確定義 |
| 版本衝突 | 說明有其他版本，禁止靜默覆寫 | 比較、重新載入、建立副本或人工解決 |
| 再次嘗試 | 顯示作用目標與結果 | 保持冪等，避免重複建立紀錄 |

前端計時器、debounce 完成或 local state 更新不能作為「已儲存」證據。離頁保護是否解除，應以目前編輯版本與後端確認版本一致為準。

## 8. Sticky Action Bar

### 8.1 候選內容與層級

- 暫存草稿：正式持久化完成前，在 Prototype 中不可偽裝成可保存功能；可不呈現，或以明確「Prototype 不提供保存」說明取代。
- 取消：次要或文字動作；有未保存內容時進入捨棄確認。
- 上一步／下一步：分段流程中的主要導覽動作。
- 送出紀錄：只在第六區段作主要 CTA，名稱不可簡化為模糊的「完成」。

### 8.2 版面與退化條件

- 頁面內容底部 padding 至少涵蓋 Action Bar 實際高度、間距與 safe-area，最後一個欄位及錯誤不可被遮住。
- iPhone 使用 `env(safe-area-inset-bottom)`，無支援時仍保有正常 padding。
- 軟體鍵盤開啟時，Action Bar 不可遮住目前輸入框；需測試 viewport resize、virtual keyboard overlay 與捲動到欄位。
- 200% zoom 時允許按鈕換行或改為垂直排列，不得截字、重疊或產生雙向捲動。
- Backdrop blur 只作裝飾；底層必須有足夠不透明的 Surface、上邊界或陰影。`backdrop-filter` 不支援時資訊層級不變。
- reduced motion 下取消滑入、彈跳與不必要 transition。
- forced-colors 下保留可辨識邊界、按鈕文字與 focus，不依賴透明背景。

### 8.3 誤觸防護

- 操作列位置保持穩定，送出按鈕不因狀態更新突然取代下一步的位置。
- 送出時若有錯誤，不開啟確認；先顯示錯誤摘要。
- 送出確認要顯示個案、紀錄類型、服務時間與關鍵追蹤摘要；確認後顯示處理中並防止重複送出。
- 可逆導覽不過度使用 modal；只有捨棄未保存內容或送出等高影響操作要求確認。

## 9. Responsive 行為

| Viewport | 主要佈局 | 表單與導覽 | Action Bar |
| --- | --- | --- | --- |
| `320px` | 單欄、`16px` gutter；不允許頁面水平捲動 | 一次一區；標題、錯誤與長文字可自然換行 | 動作可垂直排列或主要 CTA 滿寬；保留 safe area |
| `375px` | 單欄、`16px` gutter | 同 320px，可容納清楚進度與返回 | 依文字長度決定雙欄或垂直，不壓縮觸控目標 |
| `768px` | 單欄主內容或窄雙欄；閱讀欄維持適中 | Tabs 僅在完整標籤與 200% zoom 可用時採用，否則退化 | 可水平排列，但需預留鍵盤與 viewport 高度 |
| `1440px` | 左側導覽＋右側主內容；容器置中 | 左導覽可 sticky，主表單保持單一閱讀欄，不把六段攤成多欄 | 與主內容欄對齊，不橫跨到導覽造成關係模糊 |

共同規則：

- 以內容需要而非裝置名稱決定 breakpoint。
- 長篇文字、錯誤訊息、中文與英數混排皆可換行；ID 或長字串使用安全斷行。
- 200% zoom 視為必要版面，不另做「桌面縮小版」。功能、欄位與錯誤不得因放大消失。
- 瀏覽器文字放大時不可用固定高度裁切文字。
- 橫向平板與外接鍵盤情境須納入測試。

## 10. Accessibility

### 10.1 鍵盤與 focus

- 所有功能可用鍵盤完成，Tab 順序符合視覺與閱讀順序。
- 提供跳至主要內容；導覽、表單、錯誤摘要與 Action Bar 使用清楚 landmark／heading 結構。
- Focus 必須清楚、持續且不被 sticky 元件或 overflow 裁切。
- Dialog 開啟時移入 focus、限制在 dialog 內，關閉後回到觸發元件；Escape 行為須符合是否會造成資料遺失的風險。
- Tabs、Accordion 與步驟導覽須採對應標準鍵盤模式，不自行創造只能點擊的交互。

### 10.2 Label、說明與錯誤

- 每個欄位有永久可見 label，並以程式關聯；placeholder 只能提供格式範例。
- 補充說明、單位、字數限制與錯誤用 `aria-describedby` 或等價方式關聯。
- 必填與無效狀態可被輔助科技辨識；錯誤訊息須說明問題及修正方式。
- 送出錯誤摘要應在更新後可被察覺，且每項錯誤能導向欄位。
- 自動保存或送出狀態若未來實作，live region 應節制，避免每次輸入都朗讀。

### 10.3 視覺、縮放與偏好

- 檢查一般文字、large text、控制項邊界、focus、圖示與各狀態的實際對比。
- 狀態使用文字，必要時加圖示；不可只靠藍、綠、黃或位置辨識。
- 於 320px、375px、768px、1440px 及 200% zoom 實測，不截字、不遮欄位、不失去功能。
- `prefers-reduced-motion: reduce` 下移除非必要動態與平滑捲動；狀態改變仍須可理解。
- forced-colors／高對比模式至少保留控制項邊界、focus、目前項目、錯誤與按鈕層級；陰影、背景色與 blur 消失後仍可用。
- 不以 hover 才揭露必要資訊；觸控、鍵盤與滑鼠取得相同內容。
- 圖示按鈕提供可辨識名稱，裝飾圖示對輔助科技隱藏。

### 10.4 驗證方式

實作 Gate 前至少規劃：鍵盤走查、主流螢幕閱讀器 smoke test、瀏覽器 200% zoom、窄 viewport、forced-colors 或等價高對比檢查、自動化 accessibility scan，以及含長文字與多錯誤狀態的人工檢視。自動化掃描不能取代人工與專業人員測試。

## 11. Dark Mode Defer 條件

Dark Mode 列為後續階段，第一版不實作。候選基礎色僅供未來探索：

| Token | 候選值 |
| --- | --- |
| Canvas | `#0F172A` |
| Surface | `#1E293B` |
| Primary Text | `#E2E8F0` |

必須全部滿足後才可開啟正式實作 Gate：

- 品牌方提供並核准深色背景用的正式淺色 WinWin Logo。
- 所有狀態色完成暗色模式對比與非色彩語意檢查。
- Input、Textarea、錯誤、focus、hover、disabled、read-only、selection 與 autofill 狀態完整定義。
- 圖表、附件預覽與列印模式有獨立策略；列印不得直接輸出深色大面積背景。
- 定義使用者偏好、system preference、首次預設與跨裝置保存方式。
- 完成真實裝置與輔助科技驗證。

不得用 CSS filter 將現有黑色透明 Logo 反白作為正式品牌素材。

## 12. 建議的第一條專業紀錄 Prototype Flow

### 12.1 Flow 範圍

第一條 Prototype 只驗證「專業人員為一位既有個案新增一筆一般照顧／服務紀錄」；不建立新個案、不驗證權限、不寫入後端，也不模擬真的自動儲存。

```text
個案歷程（既有虛構個案）
  → 新增專業紀錄
  → 看見 Prototype 資料保存限制
  → 1. 本次服務基本資訊
  → 2. 觀察與主述
  → 3. 評估內容
  → 4. 處置或服務紀錄
  → 5. 後續追蹤
  → 6. 確認與送出
  → Prototype 完成畫面／返回虛構個案歷程
```

### 12.2 每區最低內容

| 區段 | Prototype 最低內容 | 核心驗證目的 |
| --- | --- | --- |
| 基本資訊 | 個案摘要（唯讀）、服務日期時間、紀錄類型、專業人員 | Label、日期時間輸入、唯讀與可編輯辨識 |
| 觀察與主述 | 一個長篇 Observation textarea、來源或主述者 | 長文輸入、自動增高、閱讀行長 |
| 評估內容 | 結構化選項加補充說明 | 選項群組、鍵盤操作、條件欄位 |
| 處置或服務 | 可複數的服務項目、長篇紀錄 | 重複項目、防誤刪、長內容掃讀 |
| 後續追蹤 | 是否追蹤、期限、負責角色、注意事項 | 條件式內容、狀態語意、日期與責任清楚度 |
| 確認與送出 | 六區摘要、缺漏與錯誤連結、送出確認 | 跨區錯誤、可逆返回、誤送防護 |

### 12.3 Prototype 誠實邊界

- 使用虛構個案與虛構紀錄，不放入任何真實個資或健康資訊。
- 輸入只存在目前頁面／session 的記憶體，重新整理後重置。
- 「送出」只示範流程終點，不得以成功訊息暗示資料已寫入正式系統；完成文案應明示「流程展示已完成，未建立正式紀錄」。
- 不加入假儲存 API、假時間戳、Supabase 呼叫或資料庫 schema。
- 離頁警告是 flow 的必要測試狀態，不代表 Prototype 已具可靠防遺失能力。

## 13. 必須透過專業人員測試驗證的問題

建議邀請實際會長時間讀寫個案紀錄的角色，使用虛構但貼近工作的情境完成任務；角色與樣本策略由研究計畫另定。至少驗證：

1. 六個區段名稱是否符合專業人員心智模型，哪些欄位常跨區或順序不同？
2. 手機步驟式與 Accordion 何者更容易定位、回查與修正前段內容？
3. 平板 Tabs 在橫向、直向、200% zoom 與外接鍵盤下是否仍清楚？
4. Desktop 左側導覽是否幫助定位，還是造成視線與操作移動負擔？
5. 使用者能否正確理解「已完成區段」「尚未填寫」與「有錯誤」，而不只依賴顏色？
6. 跨區錯誤摘要是否能讓使用者找到、修正並返回確認位置？
7. 長篇 Observation 的字級、行高、行長與 textarea 高度是否適合真實內容量？
8. Textarea 自動增高、內部捲動與手動 resize 哪種組合較可預期？
9. Prototype 的保存限制是否在輸入前就被理解；使用者是否誤以為暫存或送出會永久保存？
10. 離頁警告是否清楚且不過度干擾正常導覽？
11. Sticky Action Bar 是否遮擋內容、鍵盤或錯誤，且各按鈕是否有誤觸風險？
12. 「暫存草稿」「下一步」「送出紀錄」的名稱與視覺層級是否能避免混淆？
13. 確認頁提供哪些資訊才足以防止送錯個案、日期或紀錄類型？
14. 狀態 Pill 的文字、圖示與色彩是否能被不同視覺能力的使用者理解？
15. 鍵盤與螢幕閱讀器使用者能否完成全流程、察覺錯誤與確認結果？
16. 320px、375px、768px、1440px 與 200% zoom 是否保留完整功能與可讀性？
17. 介面是否仍被辨識為 WinWin，同時足夠沉靜且不顯得像傳統醫療表格？

測試記錄應保留任務完成狀況、關鍵錯誤、理解偏差、原話摘要與裝置／輔助科技條件；小樣本觀察只能作為迭代訊號，不能直接推論整體成效。

## 14. Gate 判定與後續實作邊界

### 14.1 本輪 Gate：Design Review only

本輪可接受產出只有本設計文件與文件層級驗證。明確不包含：

- 修改前端、現有 CSS 或元件。
- 建立專業紀錄 route 或新畫面。

- 修改 Migration、Supabase schema、資料、設定或 Production。

### 14.2 下一階段進入 Prototype 前的 Gate
