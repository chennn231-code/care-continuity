# 備份心｜Low-Fi Wireframe Baseline v0.9.9

> 本文件是 Screen 01–09 的文字式低擬真 Wireframe 基準，用於後續繪製灰階 Low-Fi、Case Walkthrough 與可用性測試前的流程校正。

## 0. 設計原則

- 幫家庭盤點與準備，不診斷、不評分。
- 不自動推測誰一定能幫忙。
- 不因沒有備援而阻擋流程。
- 不使用未經驗證的高／中／低風險或分數。
- 不把正式服務的存在直接視為任何時段都可用。
- 不把偶發事件誤算成每日固定缺口。
- 所有輸入都應能追溯到明確產品用途。

# Screen 01｜定位

### 目的
傳達備份心的用途，建立「盤點與準備」的產品定位。

### 文案
**備份心**

**為照顧，多準備一個如果**

一起整理家裡目前的照顧安排，看看如果臨時有狀況，哪些事情已有安排、哪些還可以先準備。

### CTA
`開始盤點`

### 備註
- 不顯示未經測試的完成時間。
- 不使用英文品牌副名。
- 本頁不收集個人資料。

---

# Screen 02｜我是誰

### 目的
確認操作者角色，供後續語句與資料帶入使用。

### 選項
- 被照顧者本人｜想先為自己的照顧安排做準備
- 主要照顧者｜平時主要由我安排或執行照顧
- 共同照顧者｜與其他家人分工處理日常照顧
- 遠距關心／協調者｜不在身邊，但協助協調或負擔費用
- 其他

### 規則
- 不預選。
- 若為操作者本人參與照顧，後續 CareSource 可帶入「我」。

---

# Screen 03｜為誰準備

### 目的
建立最小化的被照顧者識別資訊。

### 欄位
- 暱稱／稱呼
- 關係

### 隱私文案
僅蒐集完成備援盤點所需的最低限度資料，降低不必要的識別資訊蒐集。

### 不收集
- 身分證字號
- 完整生日
- 完整病歷
- CMS 等級
- 健保資料

---

# Screen 04｜需要什麼

### Data Model
`CareTask`

### 目的
盤點目前需要他人協助的日常事項；若目前大多能自理，則進入預防性準備分流。

### 卡片
- 吃飯
- 準備餐食
- 吃藥
- 上廁所
- 上下床／移動
- 洗澡／清潔
- 穿脫衣物
- 外出／就醫
- 其他

### 額外選項
`目前這些事情大多可以自己處理`

### 分流
若選「大多可以自己處理」，不可直接進情境模擬。先詢問是否有希望提前準備的事項；若有，建立 `PREPARED_IN_ADVANCE` 任務；若沒有，可完成簡化設定。

### 用語限制
不出現 ADL、IADL、失能程度或風險評分。

# Screen 05｜怎麼幫＋什麼時候發生

### Data Model
`TaskRequirement` + `TaskOccurrence`

### 目的
了解每一個已選任務平常如何被協助，以及大致何時發生。

### 互動
- 使用同一 Screen Template 逐項切換任務。
- 顯示任務內進度，例如 `1 / 4`。
- 不為了省時間自動套用答案。
- 提供「我現在不太確定／稍後補充」。

### 協助方式
依任務使用不同題庫，不共用單一「程度」量表。

例：

**如廁**
- 有人在附近，需要時能幫忙
- 需要提醒或引導
- 需要實際扶持或動作協助
- 每次情況不太一樣
- 我現在不太確定

**服藥**
- 需要提醒
- 需要準備藥物
- 需要實際協助服用
- 情況不固定
- 我現在不太確定

### 發生時間
- 每天
- 特定星期
- 特定日期
- 不固定／需要時

若選每天，再問：
- 時間大致固定
- 不固定

若大致固定，可用早上／中午／下午／晚上／自訂時間。

### Help `?`
**為什麼要知道時間？**

備份心會用這些時間，看看原本照顧的人不在時，哪些照顧安排可能需要另外準備。大概填寫即可，之後都能修改。

# Screen 06｜現在誰幫

### Data Model
`CareSource` + `CoverageAssignment(PRIMARY_CURRENT)`

### 目的
將每項照顧任務連接到目前實際參與的人或服務。

### 互動
- 任務對應人／服務。
- 同一任務允許多人或多來源。
- 操作者可作為「我」直接帶入。
- 可新增家人／親友／正式服務。
- 允許 `目前沒有固定安排`。

### 正式服務
需記錄：
- 實際服務內容
- 大致服務日期／時段

不得因「有居服／日照」就推定其他任務或其他時段也已被覆蓋。

### 隱私
不要求機構統編、核定碼、合約或服務人員真實姓名等非必要資料。

# Screen 07｜還有什麼方式能接

### Data Model
`CoverageAssignment(BACKUP)` + `backup_review_status`

### 目的
逐任務盤點當主要照顧來源暫時不可用時，是否已有其他人、服務或方式可能承接。

### 第一層選項
- 目前還沒有
- 有其他人或服務可能可以
- 我不確定

### 若有候選來源
追問確認狀態：
- 可能可以｜尚未確認
- 已經談過｜由使用者標記已和對方確認
- 有條件限制

### 限制候選
- 特定時間
- 限短時間
- 距離較遠
- 僅能遠距聯絡／協調
- 其他

### 批次操作
若使用者選擇批次將其餘未填項目設為「目前還沒有」，必須二次確認：

> 其餘 X 項目前也都還沒有其他安排嗎？

- 是，都是目前沒有
- 我想逐項確認

### 重要規則
- `POSSIBLE` 不等於已安排。
- 使用者標記 `CONFIRMED` 不等於本人已驗證。
- 沒有備援是有效資料，不應出現錯誤阻擋。

# Screen 08｜設定一個「如果」

### Data Model
`Scenario`

### 目的
指定某個照顧來源在某段期間無法提供原本支援，進行備援覆蓋檢查。

### MVP 首次情境
預設語境可聚焦主要照顧者／操作者暫時無法提供原本照顧，但底層保留未來指定任一 CareSource 的能力。

### 選項
全部預設未選：
- 幾個小時
- 1 天
- 3 天
- 7 天
- 自訂區間
- 目前不知道會多久

### CTA
選擇後才啟用：

`看看這段時間的照顧安排`

### 規則
- 不預選 3 天。
- 不使用「隨機看 3 天」。
- `UNKNOWN_DURATION` 不應任意假設恢復時間。

# Screen 09｜看哪些已有安排、哪些待確認、哪些待準備

### Data Model
讀取 Coverage Result；使用者建立待辦時寫入 `ActionItem`。

### 目的
將情境運算結果轉換成使用者可理解、可行動的整理結果。

### 三態
- 已經有安排
- 還需要確認
- 還需要準備

### 呈現原則
- 優先以時間順序呈現真正會發生的 TaskOccurrence。
- `AS_NEEDED` 項目不自動塞進每日時間軸。
- 連續同類空窗應合併，避免資訊轟炸。
- 正式服務只顯示「依目前既有安排可覆蓋」，不保證未來一定提供。

### 開頭
**可以先從這件事開始準備**

例：

```text
8/25 08:00｜吃藥
△ 還需要準備
目前尚未記錄其他承接安排
```

### 非固定事項
另設「視情況發生的事項」區塊，不誤算成固定缺口。

### 結尾
你已經完成了最關鍵的第一步：把目前的照顧安排，以及還需要準備的地方整理出來。

### ActionItem
可將結果加入：
- 待確認
- 待準備

不得使用「非常安全」、「高風險」、「0 分／100 分」等保證或評分語言。

# Low-Fi 下一道 Gate

真正進入高擬真 Figma 前，需：

1. 將本規格繪製為灰階 Low-Fi 畫面。
2. 使用 Case 01–05 再跑一次介面走查。
3. 檢查是否產生假性備援、假性缺口或錯誤時間覆蓋。
4. 檢查首次設定的實際完成時間與輸入負擔。
5. 再以目標使用者進行 usability test，不以 Case Walkthrough 取代真實使用者測試。

本文件為 v0.9.9 Baseline，Low-Fi 或使用者測試發現問題時允許版本化修正。
