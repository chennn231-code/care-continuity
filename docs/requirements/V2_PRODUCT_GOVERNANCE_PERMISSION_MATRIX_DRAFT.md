## 3. Proposed Governance Baseline

> 家屬可以建立個案草稿，但在使用者聲明已取得長者本人或適當授權者同意前，不得邀請成員或分享個案資料；授權後可指定一位或多位協作管理者，專業人員僅依實際服務關係、目的、資料範圍及期限取得權限。

學生 Prototype 只能記錄使用者的授權聲明，不得宣稱系統已驗證：

- 法定代理身分
- 長者意思能力
- 電子簽章效力
- 授權文件真實性
- 正式法律同意
- 醫療或長照機構法遵

授權聲明是產品流程中的治理門檻，不是法律認證結果。正式上線前仍需法律、隱私、資安與長照實務審查。

## 4. 角色定義

| 角色 | 定義 | 不自然取得的權限 |
|---|---|---|
| 個案建立者 | 建立個案草稿並輸入最低必要資料的人 | 不等於授權者；授權前不能邀請、分享或查看尚未建立的敏感範圍 |
| 個案授權者 | 長者本人，或使用者聲明依法可代表長者處理授權的人 | 不因授權身分自動負責所有日常管理或工作事項 |
| 協作管理者 | 在授權範圍內管理成員、角色、分享範圍及服務期間的人，可有一位以上 | 不因管理者身分自動看到所有家屬限定、專業限定或敏感健康資訊 |
| 家庭照顧成員 | 經邀請及接受後參與家庭照顧的人 | 家屬關係本身不自然取得全部資料或管理權 |
| 專業照顧成員 | 因實際專業服務關係、目的與期間參與的人 | 專業證照或職稱本身不自然取得個案權限；服務結束後不持續存取 |
| 長者本人帳號 | 長者選擇建立帳號後查看及管理自身授權的入口 | 長者本人不被強制建立帳號；無帳號不代表可以忽略授權治理 |
| 所屬機構／服務單位關係 | 用來證明或描述專業成員的服務關係與期限 | 機構不成為長者個案的永久 owner，也不因僱傭關係取得全部個案資料 |
| 組織管理者（Defer） | 未來機構版用來管理組織成員與服務關係的角色 | 第一階段不實作；即使未來存在，也不自然取得組織內所有個案或敏感內容 |

補充原則：

- 同一人在不同個案中可以有不同角色
- 同一人可能同時具有家庭與專業關係，權限仍須依當下目的及資料範圍判斷
- 多重角色不得透過權限聯集自動突破較嚴格的資料限制；每次操作仍採第 8 節的全部條件交集及最小權限原則
- 新增另一位協作管理者必須取得個案授權者同意

### 4.1 第一階段專業參與模式

- 第一階段不建立完整組織管理後台，也不建立可管理機構所有個案的組織管理者權限
- 家屬針對特定長者個案邀請個別專業人員
- 專業人員只能存取被明確邀請且仍在有效期間內的個案
- 專業人員填寫的機構、職稱及服務關係均屬使用者聲明
- 介面及測試必須標示「身分及機構關係未經正式驗證」
- 隸屬某機構不代表可以查看該機構所有個案
- 同一機構的其他人員不會自動取得個案權限
- 組織管理者、組織成員目錄、機構級個案清單與正式機構驗證全部移至後續機構版

## 5. 個案生命週期

### 5.1 候選狀態

| 狀態 | 產品語意 | 允許的主要行為 | 禁止或限制 |
|---|---|---|---|
| `DRAFT` | 建立者尚未聲明取得適當授權 | 建立者可輸入最低基本資料及整理不對外分享的草稿 | 不得邀請成員、分享、匯出或讓其他人查看個案健康與照顧資料 |
| `AUTHORIZATION_DECLARED` | 建立者已完成 Prototype 授權聲明 | 記錄聲明事件及限制提示後自動進入 `ACTIVE` | 不代表身分、代理權、意思能力或法律效力已驗證 |
| `ACTIVE` | 授權聲明有效且協作圈已啟用 | 依角色、關係、資料類型、目的及期間協作 | 不得突破原始資料分享範圍 |
| `SUSPENDED` | 授權撤回、爭議、治理人中斷或其他需暫停分享的狀態 | 只允許處理爭議、恢復或封存所需的最低治理操作 | 預設停止所有家庭及專業成員的線上內容存取、邀請、分享與匯出；歷史資料不自動刪除 |
| `ARCHIVED` | 個案不再進行日常協作但需依保留規則保存 | 符合保留與授權規則者可唯讀查看必要歷史 | 不得新增日常照顧內容或新邀請；重新啟用規則為 TBD |

### 5.2 建議轉換

```text
DRAFT
  → AUTHORIZATION_DECLARED
  → ACTIVE
  → SUSPENDED
  → ACTIVE（問題解除後，條件 TBD）
  → ARCHIVED
```

- 個案建立者可建立 `DRAFT`
- 授權聲明前只收最低必要資料，例如個案顯示名稱與草稿建立目的；不得以草稿名義蒐集完整健康或家庭資料
- Prototype 中，建立者必須聲明自己是長者本人，或聲明已獲適當授權
- 系統必須記錄聲明者、聲明時間、聲明身分、聲明版本及限制提示版本
- 完成聲明後，Prototype 由 `AUTHORIZATION_DECLARED` 自動進入 `ACTIVE`
- 只有進入 `ACTIVE` 後，才能啟用成員邀請與資料分享
- 這項自動啟用不代表法律代理權、意思能力、身分或電子同意已獲驗證
- 授權撤回時應先轉為 `SUSPENDED` 並停止新的分享，不應立即破壞性刪除歷史資料
- 授權爭議同樣使個案進入 `SUSPENDED`
- 封存後的可見範圍與保留期限必須另行定義，不能以「封存後全部人都可看」或「全部人都不可看」取代治理決策

### 5.3 帳號與個案分離

- 帳號生命週期與長者個案生命週期必須分離
- 刪除帳號不得直接造成整個長者個案 Graph 被 Cascade 刪除
- 個案不得以唯一 owner 帳號作為生命週期根
- 必須保留歷史作者顯示及不可變來源識別
- 唯一協作管理者離開前必須完成管理權轉移或將個案依規則封存
- 最後一位協作管理者不得直接退出；新管理者必須先接受管理責任，否則只能依規則封存
- 協作管理者可以有多位，但新增或移轉管理者須符合授權者同意規則
- 未授權草稿可以由建立者放棄或真正刪除
- 建立者帳號刪除前，系統必須先處理其草稿及所有管理責任
- 個案刪除、去識別化、封存及法定保存需求尚未完成定案

本節只定義產品規則，不提出 Migration、SQL 或資料表解法。

## 6. 成員生命週期

| 狀態 | 語意 | 可見與可操作範圍 |
|---|---|---|
| `INVITED` | 已發出具目的、角色、範圍及期限的邀請 | 接受前只可見邀請者、個案最低識別資訊、邀請目的、角色、資料範圍及服務期間；不得看健康內容 |
| `ACCEPTED` | 受邀者已接受邀請，但可能尚未到服務開始時間或等待啟用 | 可查看自己的加入條件，不自然取得個案資料 |
| `ACTIVE` | 接受完成且關係與服務期間有效 | 依角色、目的、資料範圍及期間存取最低必要資訊 |
| `EXPIRED` | 到達預先設定的服務結束時間 | 立即停止新的查看、下載、列印、匯出及操作；歷史作者與處理紀錄保留 |
| `REVOKED` | 授權者或具權限管理者在期限前主動撤銷 | 自撤銷生效時停止存取，並保留撤銷者、原因與時間 |
| `DECLINED` | 受邀者拒絕邀請 | 不建立資料存取權，只保留必要邀請結果供治理追蹤 |

成員規則：

- 邀請只能由個案授權者或獲授權的協作管理者發出
- 邀請必須建立在有效個案授權下
- 受邀者必須自行接受或拒絕，指派角色不等於接受角色
- 專業成員必須具有服務目的、服務開始日及服務結束日；無期限專業存取不列為第一階段預設
- 到期是預定期間自然結束；撤銷是期限前的主動治理行為，兩者必須留下不同原因與時間
- 成員離職、轉單位、轉案或服務結束時，原服務關係應到期或撤銷；新關係不得沿用舊機構權限
- 歷史紀錄可保留作者與處理歷程，但不代表離開成員仍可登入查看
- 成員到期或被撤銷時，尚未完成的處理事項必須回到待重新指派狀態，或由有權管理者取消
- 第一階段不允許管理者代替負責人標示完成

### 7.2 Conditional 條件

- **C01：** 授權者同時是新草稿的實際建立者；角色名稱不能取代真實操作人
- **C02：** 只能編輯自己建立的 `DRAFT` 最低基本資料，且不能新增敏感資料或分享
- **C03：** 個案狀態、角色權限及欄位分享範圍允許；管理者身分不自動擴張資料可見性
- **C04：** Prototype 只允許建立者聲明自己是長者本人，或聲明已獲適當授權；系統記錄聲明者、時間、身分、聲明版本及限制提示版本，但不驗證法律資格
- **C05：** 個案為有效授權狀態、操作人具有成員管理權，且操作不得超出授權者核准範圍；新增管理者另需授權者同意
- **C06：** 只能處理發給自己的有效邀請；接受後仍須等待服務期間及啟用條件成立
- **C07：** 只能查看共同照顧範圍內、未超出原始資料權限的摘要
- **C08：** 成員為 `ACTIVE`，操作目的與資料範圍允許，並保存作者、來源及時間
- **C09：** 必須是該安排指定的確認角色或具明確確認權；確認規則不得由管理者身分自動取得
- **C10：** 只能指派給協作圈內符合角色、目的、分享範圍及有效期間的人；指派後直接進入 `PENDING_ACCEPTANCE`
- **C11：** 只有被指派者能接受或拒絕；只有已接受且仍具有效權限的負責人能開始及完成，第一階段禁止代理完成或管理者代結案
- **C12：** 回覆人須可查看該問題及其必要背景；回覆不自然等於問題已解決
- **C13：** 只有問題提出者或具有該問題治理權限的角色可以標示解決；回答者或處理事項負責人不因回答或完成工作而自動取得解決權
- **C14：** 只限明確列入家屬限定範圍的人；授權者、管理者或長者帳號均不自動取得全部家屬私密內容
- **C15：** 只限特定專業目的及服務期間；授權者、管理者及長者帳號是否可查看特定專業原始紀錄需按資料類型另定
- **C16：** 管理者不得撤銷授權者、突破授權範圍或造成最後一位管理者消失；撤銷管理者可能另需授權者同意
- **C17：** 管理者只能提出或執行已由授權者同意的轉移；不得自行擴張管理者群組
- **C18：** 只能匯出操作者原本可見且被選入摘要的最低必要資料；輸出後無法技術性收回，須顯示版本與敏感資訊提醒
- **C19：** 管理者封存須有授權者同意或符合尚待定義的治理例外；長者帳號須能證明本人的授權地位
- **C20：** 刪除帳號前不得造成個案失去治理；最後一位管理者須先完成轉移或封存，個案資料不得隨帳號 Cascade 刪除

- **T01：** 個案刪除權、等待期、共同同意、法定保存、去識別化與復原機制尚未定案；第一條 v2 Vertical Slice 不提供破壞性個案刪除

## 8. 第一階段分享範圍與判斷規則

第一階段不做任意欄位級權限，只使用四種固定分享範圍：

| 分享範圍 | 語意 |
|---|---|
| `AUTHOR_ONLY` | 只有作者本人可查看；治理與安全事件所需的最低系統處理除外 |
| `SHARED_CARE` | 個案內具有相符目的與有效能力的共同照顧成員可查看 |
| `FAMILY_ONLY` | 個案內具有家庭關係且符合目的及有效期間的成員可查看 |
| `DIRECT_PARTICIPANTS` | 只有該觀察、安排、問題或處理事項明確列出的參與者可查看 |

每次授權判斷必須同時符合：

1. 個案狀態
2. 成員狀態
3. 角色能力
4. 與個案的關係
5. 使用目的
6. 紀錄分享範圍
7. 有效期間

判斷採全部條件交集及最小權限原則。任何一項不允許即拒絕；任何單一角色、關係或管理權都不能單獨提升資料權限。

| 資料類型 | 第一階段規則 |
|---|---|
| 個案最低基本資料 | 只對辨識協作個案所需的人提供最低資料，不公開完整身分資訊 |
| 有來源的觀察 | 建立時必須選擇固定分享範圍，並保留作者、來源及版本 |
| 照顧安排 | 只對提議、確認、執行或必要知悉者開放 |
| 處理事項 | 至少對指派者、負責人及必要參與者開放，不因此公開所有背景資料 |
| 問題與回覆 | 依固定分享範圍及直接參與者控制，不形成無限制聊天室 |
| 權限與操作歷程 | 只提供完成治理責任所需的最低事件，不代表可看完整安全稽核 |

固定原則：

- 協作管理權不自然包含敏感內容查看權
- 專業人員只在服務目的及期間內取得最低必要資訊
- 家屬不能查看所有專業原始紀錄
- 歷史紀錄存在不代表已離開成員仍可查看
- 第一階段不儲存或分享正式病歷、診斷、完整護理紀錄或機構法定紀錄
- 摘要及列印的衍生資料規則見第 11 節，不能用衍生內容繞過來源權限

## 9. 獨立狀態模型

不同 Domain Object 不共用單一「已確認」狀態。

### 9.1 觀察

觀察是有來源的陳述，不代表專業判斷或事實已獲證實。每筆至少保留：

- 作者
- 發生時間
- 紀錄時間
- 來源，例如本人觀察、家屬轉述、專業服務紀錄摘要
- 是否需要進一步確認

例如「家屬觀察到最近洗澡時站立較不穩」只能呈現為該家屬的觀察，不得自動轉成診斷。

### 9.2 照顧安排

候選狀態：

- `Proposed`
- `Needs Confirmation`
- `Confirmed`
- `Cancelled`

確認者須是該安排指定且獲授權的角色。主要照顧者自行記錄不等於所有受影響者都已確認。

### 9.3 處理事項

第一階段固定狀態：

- `PENDING_ACCEPTANCE`
- `ACCEPTED`
- `IN_PROGRESS`
- `COMPLETED`
- `DECLINED`
- `CANCELLED`

固定原則：

- 指派對象、指派者及指派時間是事件資料，不另設 `ASSIGNED` 狀態
- 指派後進入 `PENDING_ACCEPTANCE`
- 只有被指派者能接受或拒絕
- `ACCEPTED` 不等於 `IN_PROGRESS`，`IN_PROGRESS` 不等於 `COMPLETED`
- `COMPLETED` 只表示負責者聲明處理完成，不自動代表相關問題已解決
- 到期或成員撤銷時，未完成事項必須回到待重新指派狀態，或由有權管理者取消
- 第一階段不允許管理者代替他人標示完成
- 完成者、完成時間、狀態轉換者及時間必須可追溯

### 9.4 問題

第一階段固定狀態：

- `OPEN`
- `ANSWERED`
- `RESOLVED`
- `REOPENED`

- 有人回答不等於問題已解決
- 處理事項完成不會自動把問題改為 `RESOLVED`
- 只有問題提出者或具有該問題治理權限的角色可以標示 `RESOLVED`
- 新資訊出現時可以進入 `REOPENED`
- `CLOSED` 暫緩到後續階段，不列入第一階段狀態機

第一階段 Proposed Domain Decision 是讓 Question 與照顧更新共用核心來源、時間、分享範圍及狀態歷程能力，並可連結零至多個處理事項，以避免同時建立大型聊天室與另一套大型任務系統。正式物件邊界留待 Domain Model Design Review，不在本文件建立資料表名稱。

本決定只屬 Domain Direction，不是正式資料表或 Migration 設計。

### 9.5 紀錄更正、撤回與版本

- 已發布的觀察、問題回答及完成說明不得直接覆蓋
- 原始作者、原始內容、發生時間及建立時間必須保留
- 更正以新增紀錄完成，新紀錄以不可變引用指向被更正的紀錄
- 畫面預設顯示最新有效版本，並明確標示內容曾經更正
- 原作者失去權限後，只有明確具有該資料類型更正權限的人可以提出更正
- 更正者不得被顯示為原作者
- 問題及處理事項保留建立當時連結的來源版本，同時可以提示來源已有更新版本
- 未發布草稿可以真正刪除
- 已發布內容原則上只能撤回或由新版本取代，不得直接消失
- 撤回仍須保留 Audit Event、來源關係及必要原因

## 10. 第一階段最小 Audit Event

第一階段至少記錄：

- 授權聲明、撤回及爭議
- 個案狀態轉換
- 邀請發出、接受、拒絕、撤回及到期
- 成員啟用、暫停、撤銷及期限變更
- 角色、目的及分享範圍變更
- 觀察建立、更正及撤回
- 問題建立、回答、解決及重新開啟
- 處理事項指派、接受、拒絕、開始、完成、取消及重新指派
- 摘要、PDF 或列印資料產生及匯出

每項事件至少記錄：

- event type
- actor
- case
- target entity
- event time
- previous state
- new state
- reason 或完成追溯所需的最小 metadata

一般頁面瀏覽及所有閱讀行為的完整 Audit 可延後，但不得因此省略上述治理與狀態變更事件。

## 11. 摘要、列印與離線交接治理

摘要及離線輸出必須依下列交集產生：

`產生者可見範圍 ∩ 預定接收者可見範圍 ∩ 交接目的範圍 ∩ 來源紀錄分享範圍`

任何一個範圍不允許的內容都不得進入摘要。產生摘要、列印或匯出不會擴張來源權限，也不得將完整專業紀錄分享給不需要的人。

摘要至少保存：

- 產生者
- 產生時間
- 預定接收者或接收角色
- 權限評估時間
- 摘要版本
- 來源紀錄的不可變引用
- 來源紀錄版本及最後更新時間
- 輸出形式
- 紙本及 PDF 匯出後無法遠端撤回的提醒

本節規則標示為 **Phase 4 實作**。第一條核心 Vertical Slice 不要求先實作 PDF、列印或摘要輸出，因此本節不阻擋 Update／Action Vertical Slice；但後續實作前必須遵守本節權限交集與追溯規則。

## 12. 第一條 v2 Vertical Slice

1. 家屬建立一位長者的個案草稿
2. 使用者聲明自己是長者本人，或聲明已取得適當授權；系統記錄聲明資料及限制提示版本
3. 個案由 `AUTHORIZATION_DECLARED` 自動進入 `ACTIVE`
4. 建立照顧協作圈
5. 邀請另一位家屬，或邀請一位具有服務目的與期限、身分關係尚未正式驗證的個別專業成員
6. 對方接受邀請，並在有效期間開始後取得最低必要權限
7. 家屬新增一筆包含作者、時間、來源及分享範圍的照顧變化
8. 指派一項處理事項，狀態進入 `PENDING_ACCEPTANCE`
9. 被指派者接受，開始處理並由本人標示完成
10. 雙方依權限查看作者、來源、時間、更正標示及狀態歷程
11. 相關問題由問題提出者或具治理權限者獨立判斷是否解決，不因處理事項完成而自動結案
12. 專業服務期間結束後，該專業成員的線上存取立即到期；未完成事項重新指派或由有權管理者取消

同一流程以角色、目的、分享範圍及期間參數化，可支援：

- **家屬與家屬：** 共同處理家庭照顧變化及工作事項
- **家屬與日照：** 分享日照服務所需的最低必要資訊，追蹤指定問題或服務事項，服務關係結束後停止存取
- **家屬與居服：** 在居服服務目的與排定期間內分享最低必要資訊並追蹤處理事項
- **家屬與其他專業角色：** 依該專業服務目的、資料範圍及期間授權，不因職稱取得完整個案

此 Vertical Slice 驗證的是 Update／Action 治理與協作流程可理解性，不包含 Phase 4 摘要或 PDF 實作，也不證明法律效力、臨床成效、專業身分真實性或 Production 安全性。

## 14. 驗收問題回答

| 問題 | Proposed Baseline 回答 |
|---|---|
| 誰能建立草稿 | 家屬建立者或長者本人帳號；授權者若親自操作也可成為建立者 |
| 何時才能邀請 | 使用者完成適當授權聲明，且個案進入可啟用協作的狀態後 |
| 誰能管理成員 | 個案授權者及授權範圍內的協作管理者 |
| 誰能看到哪些資料 | 由角色、個案關係、資料類型、分享範圍、目的及有效期間共同決定 |
| 誰能指派 | 獲授權且可查看必要上下文的協作者；不得跨越成員角色及服務範圍 |
| 誰必須接受 | 被指派的本人；指派者不能代替對方接受 |
| 誰能完成 | 被授權且已接受該事項的負責人；第一階段不允許管理者或他人代理完成 |
| 權限何時到期 | 預設在服務期間結束、主動撤銷或個案進入停止分享狀態時 |
| 最後一位管理者如何保護 | 禁止直接退出，必須先完成管理權轉移或依規則封存 |
| 帳號刪除時個案如何持續 | 個案生命週期必須與帳號分離，刪帳前完成治理移轉，且不得 Cascade 刪除個案 Graph |
| 摘要與列印如何遵守原始權限 | 採產生者、預定接收者、交接目的及來源分享範圍的交集，並保留來源版本與輸出追溯資料；Phase 4 才實作 |
| 哪些規則仍為 TBD | 詳見第 15 節 |

## 15. Phase 0.1 決策分層、BLOCKER 與 Defer

### 15.1 本輪已解決的治理衝突

- Prototype 授權流程固定為 `DRAFT → AUTHORIZATION_DECLARED → ACTIVE`，不再以第二人審查或冷靜期阻擋第一條 Vertical Slice
- 授權撤回或爭議固定進入 `SUSPENDED`，並預設停止家庭及專業成員的線上內容存取
- 專業參與固定為針對特定個案邀請個別人員，組織管理者延後
- 處理事項狀態已移除重複的 Assigned／Awaiting Acceptance 語意
- 問題回答、處理完成與問題解決已拆成獨立狀態與責任
- 已發布內容的更正、撤回與版本保留原則已固定
- 第一階段分享範圍及全部條件交集原則已固定
- 第一階段最小 Audit Event 已固定
- 摘要與列印已明確延至 Phase 4，不阻擋 Update／Action Vertical Slice

### 15.2 Domain Model Design Review 前必須決定

以下內容必須在 Domain Model Design Review 中轉成無歧義的 Domain 規則，但不得在本文件直接建立資料表或 SQL：

- 各角色對觀察、安排、問題、處理事項及更正的精確 capability 邊界
- 照顧更新、問題、處理事項與來源版本之間的關聯及不可變引用語意
- 每個狀態轉換的合法前置狀態、操作者與失敗結果
- 成員到期或撤銷時，未完成事項如何進入待重新指派而不遺失原責任歷程
- `SUSPENDED` 下最低治理操作的精確清單
- 邀請接受前最低識別資訊的固定集合

上述項目完成 Domain Model Design Review 後，才能評估資料模型；目前不得直接進入 Migration 007 實作。

### 15.3 Migration 007 實作前的硬性 BLOCKER

- **BLOCKER-01 — 個案與帳號生命週期耦合：** 個案不得以唯一 owner 帳號作為生命週期根，刪除或停用帳號不得 Cascade 刪除個案
- **BLOCKER-02 — 歷史作者與來源持續性：** 帳號離開後仍須保留歷史作者顯示、不可變來源識別、更正鏈與狀態事件
- **BLOCKER-03 — 最後管理者保護：** 最後一位協作管理者不得離開，除非新管理者已接受，或個案已依規則封存
- **BLOCKER-04 — 草稿與管理責任清理：** 未授權草稿可由建立者放棄或刪除；建立者帳號刪除前必須先處理其草稿及管理責任
- **BLOCKER-05 — 授權交集 enforcement：** 必須證明個案狀態、成員狀態、角色能力、個案關係、目的、分享範圍及有效期間的交集可被一致強制執行
- **BLOCKER-06 — 到期與撤銷即時性：** 必須保證專業服務到期或撤銷後，新的查看、下載、匯出及操作立即停止
- **BLOCKER-07 — 安全變更驗證：** 正式實作前須完成資料保留、回復、回滾、權限回歸及既有資料處理方案；不得以本文件取代技術驗證
- **BLOCKER-08 — 實作基線：** 建立 v2 開發基線前須重新執行完整測試，並處理 Coverage Engine 文件與實作版本不一致；167 項測試只屬最後紀錄

### 15.4 第一條 Vertical Slice 前必須決定

- 未驗證專業身分及機構關係的固定提示文案與顯示位置
- 授權聲明及限制提示的可測試內容版本
- 邀請資訊的最低揭露內容，避免邀請本身洩漏敏感資訊

### 15.5 後續機構版 Defer

### 15.6 法律、隱私或場域專家確認事項
